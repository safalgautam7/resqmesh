# ResQMesh — Development Phases

This file is the implementation checklist for development agents.

The rule is:

> **Do not jump to a later phase until the current phase works and its tests pass.**

The project has three stages. Stage 1 is the immediate implementation target.

---

# Stage 0 — Project Bootstrap

This is preparation, not a major product stage.

## Goal

Create a clean development environment with the agreed architecture.

## Tasks

### Repository

Create:

```text
resqmesh/
├── README.md
├── goal.md
├── architecture.md
├── phase.md
├── .env.example
├── .gitignore
├── backend/
├── frontend/
└── evaluation/
```

### Backend

Create a Django project and install:

- Django
- Django REST Framework
- PostgreSQL driver
- CORS support if required
- testing dependencies

Use a virtual environment.

### Frontend

Create a Flutter application.

### Environment

Create:

```text
.env.example
```

with placeholders for:

```text
DJANGO_SECRET_KEY
DATABASE_URL
AI_PROVIDER
AI_API_KEY
```

Do not commit `.env`.

## Stage 0 Tests

Confirm:

```bash
python manage.py check
python manage.py test
flutter test
```

The project should start successfully.

Expected state:

```text
Django: WORKING
PostgreSQL: CONNECTED
Flutter: RUNNING
Tests: PASS
```

# STAGE 1 — Core Emergency Reporting Platform

## Stage Goal

Build the first complete usable version.

After Stage 1, a citizen must be able to:

1. Register/login.
2. Open the emergency screen.
3. Submit an emergency report.
4. Attach location if permitted.
5. View their submitted reports.
6. Receive/view official alerts.

A coordinator must be able to:

1. Login.
2. View incoming reports.
3. View report details.
4. Change operational status.
5. Set priority manually.
6. Create an official alert if authorized.

The system must use Django as the source of truth.

---

# Stage 1.1 — Authentication

## Feature

Implement users and roles.

### Roles

```text
CITIZEN
COORDINATOR
ADMIN
```

## Backend Functions

Implement:

```text
register_user()
authenticate_user()
get_current_user()
```

Recommended API shape:

```text
POST /api/v1/auth/register/
POST /api/v1/auth/login/
GET  /api/v1/auth/me/
```

Use a proper token/session authentication strategy.

For a mobile API, JWT can be used if it fits the implementation.

## Required behavior

Citizen:

```text
register
login
logout
```

Coordinator/admin accounts should not be freely self-created through a public endpoint.

## Tests

- registration succeeds with valid data
- duplicate account is rejected
- invalid credentials are rejected
- authenticated user can access `/me`
- unauthenticated user cannot access protected endpoints
- citizen cannot obtain coordinator privileges through request payload manipulation


# Stage 1.3 — Emergency Report API

## Required endpoints

```text
POST /api/v1/emergencies/
GET  /api/v1/emergencies/
GET  /api/v1/emergencies/{id}/
PATCH /api/v1/emergencies/{id}/
```

Permission rules:

### Citizen

Can:

```text
POST own report
GET own reports
GET own report detail
```

Should NOT:

```text
view other citizens' private reports
change system-level priority without permission
change reporter
```

### Coordinator

Can:

```text
view reports
view report details
change status
change priority
```

### Admin

Has coordinator capabilities plus administration.

## Implementation Rule

Keep views thin.

Business logic should go into:

```text
emergencies/services.py
```

## Tests

At minimum:

```text
test_create_emergency_report
test_list_own_reports
test_get_own_report
test_citizen_cannot_view_other_report
test_coordinator_can_view_reports
test_coordinator_can_update_status
test_coordinator_can_update_priority
test_citizen_cannot_change_reporter
```

Free-text field.

Example:


### Optional Location

Provide:

```text

```

Do not make location mandatory.

### Optional people count

```text

```

Keep this simple.

## Submit button

Use clear wording:

```text
SEND EMERGENCY REPORT
```

Before submit, show a concise review state if it does not add unnecessary friction.

## Tests

- report can be submitted with location

# Stage 1.6 — Permissions

Do not ask for every permission during startup.

Use contextual permission requests.

## Notifications

Ask when enabling notifications / first relevant usage.

Reason shown to user:

> "Allow notifications so ResQMesh can show emergency alerts and updates."

## Location

Request when the citizen chooses:

```text
Add My Location
```

Reason:

> "Your location can help responders find you."

## Camera

Do not request in Stage 1 unless photo attachment is actually implemented.

## Microphone

Do not request in Stage 1 unless voice reporting is implemented.

## Bluetooth

Do NOT request yet.

Bluetooth is a Stage 3 feature.

## Tests

On a real device:

- deny notification permission
- deny location
- allow location
- check that the app remains usable
- ensure permissions can be retried through an appropriate UI
- ensure no unnecessary permission is requested at startup

# STAGE 2 — Agent-Assisted Emergency Coordination

## Goal

Make the emergency coordinator workflow substantially more useful.

The agent should help answer:

```text
What happened?
How many people may be affected?
What assistance is requested?
What information is uncertain?
What priority should a human review?
Could this report be related to another report?
```

---

# Stage 2.1 — Agent Abstraction

Create an interface independent of the model provider.

Example:

```python
class EmergencyAnalysisProvider:
    def analyze(self, report_text: str) -> dict:
        ...
```

Implement the first provider.

Keep the provider replaceable.

---

# Stage 2.2 — Extraction Agent

Input:

```text
Original emergency report
```

Output structured data.

It should extract:

- incident type,
- people affected,
- injuries,
- location hints,
- requested assistance.

Never invent missing values.

---

# Stage 2.3 — Uncertainty Agent

Output:

```text
known facts
unknown facts
uncertain facts
contradictions
```

Example:

```text
Exact building: unknown
People affected: reporter estimate
Injury severity: not medically verified
```

---

# Stage 2.4 — Priority Agent

Output:

```text
CRITICAL / HIGH / MEDIUM / LOW
```

plus reasons.

Example:

```text
Suggested priority: CRITICAL

Reasons:
- people report being trapped
- serious injury is mentioned
```

The coordinator may accept or modify the suggestion.

---

# Stage 2.5 — Duplicate/Related Incident Detection

Given two reports:

```text
Report A:
"People trapped in collapsed building near KU."

Report B:
"Old building beside KU has collapsed."
```

The agent can output:

```text
Possible related incident: HIGH
Reason: close location/time/topic similarity
```

This is a suggestion, not automatic deletion/merging.

# STAGE 3 — Offline Relay / Resilient Communication

## Goal

Allow emergency messages to move between nearby devices when normal connectivity is unavailable.

The first target:

```text
Phone A → Phone B → Phone C
```

Phone A and C do not need to meet directly.

---

# Stage 3.1 — Local Outbox

On the mobile app, store unsent messages locally.

Example:

```text
LocalOutboxMessage

message_id
report_id
created_at
expires_at
delivery_status
attempt_count
hop_count
```

---

# Stage 3.2 — Connectivity Detection

The app should determine:

```text
online
offline
```

If offline:

```text
report remains in local outbox
```

Do not lose the user's report.

---

# Stage 3.3 — Store-Carry-Forward

When another participating device becomes available:

```text
Device A
  │
  ▼
Exchange message inventory
  │
  ▼
Send missing messages
  │
  ▼
Device B stores message
```

Later:

```text
Device B → Device C
```

Eventually:

```text
Device C → Internet → Django
```

---

# Stage 3.4 — Duplicate Suppression

Every relay message needs a globally unique ID.

Before storing:

```python
if message_id_already_seen(message_id):
    discard_duplicate()
```

The system should never create unlimited duplicates.

---

# Stage 3.5 — TTL and Hop Count

Every relayed message should have limits.

Example:

```text
created_at
expires_at
hop_count
max_hops
```

Stop relaying when:

```text
current_time > expires_at
```

or:

```text
hop_count >= max_hops
```

---

# Stage 3.6 — Bluetooth

Only after the local relay abstraction and data model are stable.

The first physical target:

```text
Android Phone A
       │
   Bluetooth
       │
       ▼
Android Phone B
```

Then:

```text
A → B → C
```

Do not start by trying to support:

- Android + iOS
- nationwide scale
- background operation on every OS
- perfect mesh routing

Those are future problems.

# 4. AI Cost Strategy

Emergency communication must not require citizens to buy an AI subscription.

The architecture therefore follows these rules:

## Rule 1

Citizen does not pay per report.

## Rule 2

AI is a backend capability, not a consumer subscription feature.

## Rule 3

Core reporting works without AI.

## Rule 4

Agent provider can be replaced.

Possible future deployment:

```text
                     Agent Interface
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
        Hosted API    Self-hosted LLM   Local model
```

For the hackathon prototype, use whichever provider gives the best development speed and reliability.

Do not place provider credentials in Flutter.

# 5. Coding-Agent Instructions

When using a coding agent, give it **one bounded task at a time**.

Good:

```text
Implement Stage 1.2 EmergencyReport model.

Requirements:
- Follow architecture.md.
- Follow phase.md.
- Use Django conventions.
- Add migrations.
- Add serializer.
- Add model tests.
- Do not implement AI.
- Do not modify frontend.
- Run relevant tests.
```

Bad:

```text
Build the whole emergency system.
```

The second instruction creates uncontrolled scope and makes failures difficult to diagnose.

---

# 6. Coding Agent Workflow

For each task:

```text
1. Read goal.md
2. Read architecture.md
3. Read relevant section of phase.md
4. Inspect existing code
5. Implement smallest required change
6. Add/modify tests
7. Run tests
8. Fix failures
9. Report files changed
10. Report tests executed
11. Stop
```

The agent should not silently implement future-stage features.
